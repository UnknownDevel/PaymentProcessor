Payment Processor

Сервис асинхронной обработки платежей. Producer принимает HTTP-запросы, consumer обрабатывает события из RabbitMQ, webhook принимает уведомления о результате. PostgreSQL хранит платежи и события outbox.

Producer работает на FastAPI. POST /api/v1/payments сохраняет платёж со статусом pending и событие outbox в одной транзакции, после чего возвращает 202 и payment_id. GET /api/v1/payments/{payment_id} возвращает текущее состояние платежа. Для API нужен X-API-Key из .env, а для создания платежа также Idempotency-Key. Одинаковый ключ и одинаковые данные возвращают существующий платёж. Если данные отличаются, API возвращает 409.

Consumer работает на FastStream и подписан на очередь payments.new. При получении сообщения он проверяет соответствие события данным в БД, блокирует записи платежа и outbox на время транзакции и запускает эмуляцию платёжного шлюза. Обработка занимает от 2 до 5 секунд. Вероятность succeeded составляет 90 процентов, failed составляет 10 процентов.

Результат шлюза сохраняется до отправки webhook. Затем consumer отправляет HTTP POST на webhook_url с результатом платежа и отмечает успешную доставку. Ошибка webhook не меняет уже сохранённый результат шлюза. При повторе доставки consumer не запускает шлюз заново, если его результат уже записан в БД. После обработки сообщения отправляется ACK.

Общий код RabbitMQ находится в messaging. broker.py описывает подключение, очереди и exchange, events.py задаёт формат событий, outbox.py публикует события из PostgreSQL. Общие настройки и схемы находятся в shared, модели, сессии и миграции находятся в shared/db. У producer, consumer и webhook отдельные Dockerfile и зависимости.

OutboxPublisher запускается и в producer, и в consumer. Он выбирает неопубликованные события, у которых наступило available_at. FOR UPDATE SKIP LOCKED позволяет нескольким publisher обрабатывать разные записи. После подтверждения RabbitMQ событие получает published_at. Если брокер недоступен, событие остаётся в БД, публикация повторяется с увеличивающейся задержкой до 60 секунд.

Повторная доставка сообщений возможна при сбое между публикацией и сохранением published_at. Consumer проверяет handled_at события, webhook_sent_at и dead_lettered_at платежа, чтобы пропускать уже завершённую работу. Для webhook передаются Idempotency-Key и X-Payment-ID со значением UUID платежа.

Ошибки шлюза и webhook обрабатываются через outbox. Consumer сохраняет новое событие с увеличенным номером попытки и будущим available_at. Всего предусмотрено три попытки. При RETRY_BASE_DELAY=1.0 задержки перед второй и третьей попытками составляют 1 и 2 секунды. После третьей ошибки фиксируется dead_lettered_at и создаётся событие для payments.dlq. Уже сохранённый результат шлюза остаётся прежним, а незавершённый платёж получает failed.

Неожиданные исключения обработчика используют retry-очереди RabbitMQ. После первой ошибки consumer публикует сообщение в payments.retry.1, после второй в payments.retry.2. TTL этих очередей составляет 1 и 2 секунды при настройках по умолчанию. После истечения TTL сообщение возвращается в payments.new через default exchange с пустым именем. Номер попытки увеличивает consumer при публикации, RabbitMQ только задерживает и возвращает сообщение. После третьей ошибки сообщение публикуется в payments.dlq. Исходное сообщение подтверждается только после успешной публикации повтора, иначе возвращается в очередь через NACK.

Невалидные сообщения и события, не соответствующие данным в БД, отклоняются через reject без возврата в очередь. Для payments.new указан exchange payments.dlx, который направляет такие сообщения в payments.dlq. Все очереди durable и имеют тип quorum, сообщения публикуются persistent. DLQ хранит сообщения для разбора, автоматической обработки DLQ нет.

Webhook является отдельным Python-сервисом на FastAPI. Он принимает POST /webhook, проверяет тело по общей схеме PaymentNotification, пишет уведомление в логи и возвращает 200. Это получатель для демонстрации доставки, отдельного хранения уведомлений в нём нет. Внутри compose его адрес http://webhook:9000/webhook, с компьютера он доступен на http://localhost:9000/webhook.

Запуск из корня проекта с Docker и файлом .env:

docker compose up --build -d

Compose запускает PostgreSQL, RabbitMQ и webhook, применяет миграции через migrate, затем запускает producer и consumer после готовности их зависимостей. API доступен на http://localhost:8000.

Пример 
POST http://localhost:8000/api/v1/payments. 
Content-Type: application/json
X-API-Key: значение из .env
Idempotency-Key: уникальный str

{
  "amount": "1500.50",
  "currency": "RUB",
  "description": "Оплата заказа",
  "metadata": {
    "order_id": "order-42"
  },
  "webhook_url": "http://webhook:9000/webhook"
}

Адрес webhook в теле рассчитан на consumer, работающий в compose.

Получение платежа по payment_id из ответа на POST:

GET http://localhost:8000/api/v1/payments/{payment_id}

Передать заголовок X-API-Key со значением из .env. Idempotency-Key для GET не нужен. Ответ содержит текущий статус платежа и webhook_sent_at, который заполняется после успешной доставки уведомления.
